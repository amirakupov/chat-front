# Тестовый стенд чата на Next.js — дизайн

**Дата:** 2026-08-20
**Статус:** утверждён к реализации
**Смежное:** `2026-08-12-video-context-ai-chat-design.md` (спека самой фичи)

---

## 1. Задача

Клиенту нужно **самому проверить** чат: переписку user↔creator, ответы AI-персоны и то,
что персона знает про видео, из которого ей написали. Плюс всё, на что чат опирается:
роли, загрузка ассетов, лента, настройка персоны.

Стенд — не продукт. Его работа — сделать поведение бэкенда **видимым**, включая ошибки.
Если ключа OpenAI нет, стенд должен сказать «ai_unavailable», а не крутить спиннер.

### Границы

- Отдельный проект, `~/Desktop/Work/Toc2me-Harness`. Существующий `Toc2me-Frontend` (Vite)
  не трогаем: он — заготовка настоящего продукта, у него другая судьба.
- Красота не цель, но экраны должны читаться: клиент проходит историю, а не дёргает
  эндпоинты по списку.
- Один пользователь стенда — сам клиент, локально. Ни деплоя, ни мультитенантности,
  ни мобильной вёрстки.

## 2. Принятые решения

| Решение | Выбрано | Почему не иначе |
|---|---|---|
| Аккаунты | seed-скрипт SQL с готовыми user и creator | Регистрация требует подтверждения по письму; для демо это лишняя зависимость от почты |
| Две личности | две вкладки браузера, обычная и инкогнито | Кука одна на хост — иначе пришлось бы уходить от куки на Bearer и терять `EventSource` |
| Ассеты | полный прямой флоу: `uploads` → PUT частей → `complete` | Это продакшн-путь, и в дев-режиме он работает без изменений (`LocalStorageService`) |
| Свой id | новый `GET /api/user/me` в бэкенде | Единственная альтернатива — хардкод id из seed; она врёт про API, который настоящему фронту всё равно понадобится |
| Стиль приложения | ролевые экраны + тумблер «сырой JSON» на каждом | API-консоль не даёт увидеть поток токенов и системные сообщения — то есть ровно то, что просили проверить |

## 3. Архитектура

### Стек

Next.js 15 (App Router) + TypeScript. Все страницы — клиентские компоненты; Next здесь
дев-сервер, роутинг и типы, не более. Серверные компоненты потребовали бы второго пути
аутентификации (проброс куки на сервере) и ничего бы не добавили стенду.

Ноль UI-библиотек. Один `globals.css` на CSS-переменных. Стейт — React-контекст:
один на сессию, один на стрим. Vitest — только на два чистых модуля.

### Аутентификация: браузер напрямую в бэкенд

```
localhost:3000 (Next)  ──fetch credentials:"include"──►  localhost:8080 (Spring)
                       ◄─────Set-Cookie: access_token───
```

Прокси на Next **сознательно нет**: он может буферизовать SSE, и тогда токены поедут
пачкой в конце вместо потока. Работает напрямую по трём причинам, все проверены в коде:

1. Кука привязана к хосту `localhost` без учёта порта — её выставляет `:8080`, а отправляет
   браузер и на `:3000`, и обратно.
2. `SameSite=Lax` считает `:3000 → :8080` same-site: сайт — это схема плюс регистрируемый
   домен, порт в расчёт не идёт.
3. `SecurityConfig` уже разрешает `http://localhost:3000` с `allowCredentials(true)` и
   отдаёт `ETag` в `exposedHeaders` — без этого шаг «complete» нечем было бы наполнить.

Срок жизни куки теперь равен сроку токена (24 ч), так что длинный стрим не умрёт через час.

### Поток данных чата

```
USER (вкладка 1)                 BACKEND                      CREATOR (вкладка 2, инкогнито)
     │                              │                                    │
     ├─ POST /conversations ────────►│  (creatorId, assetId из ленты)    │
     ├─ POST .../messages ──────────►│                                    │
     │                               ├── AFTER_COMMIT ───────────────────►│  event: message
     │◄──── event: message ──────────┤                                    │
     │◄──── reply-start ─────────────┤  @Async: генерация                 │
     │◄──── token × N ───────────────┤                                    │
     │◄──── reply-end (messageId) ───┤                                    │
     │◄──── event: message (ответ) ──┤── то же и креатору ───────────────►│  event: message
```

Стенд обязан показать это как есть: у user'а пузырь набирается токенами, у креатора
появляется целиком — креатор не получает `token`, только `message`. Это не баг, а
следствие того, что стрим ответа адресован визитёру.

## 4. Изменение в бэкенде: `GET /api/user/me`

Единственная правка бэкенда во всей работе.

```java
@GetMapping("/user/me")
public UserDto me(@AuthenticationPrincipal UserAdapter principal) {
    return UserMapper.toDto(principal.user());
}
```

**Зачем.** Сейчас клиент не может узнать свой id: subject токена — email, в claim'ах только
`role` и `firstTimeLogin`. Из-за этого `PATCH /api/user/update/{id}` невозможно вызвать —
id взять негде, кроме ответа `become-creator`. Это дыра в API, а не неудобство стенда.

`UserAdapter` уже держит перезагруженного из базы пользователя, так что ответ всегда
свежий — роль, изменённая минуту назад, видна сразу, в отличие от claim'а в токене.

Тест: `UserControllerTest.meReturnsTheCallerFromTheDatabase`.

## 5. Seed-скрипт

`scripts/seed-demo-users.sql` в репозитории бэкенда.

Логин требует `account_status = 'ACTIVE'` (`AuthService.loginAndGetToken`), а его ставит
только подтверждение письма. Скрипт ставит статус напрямую — почта из уравнения уходит.

Создаёт:

| Email | Пароль | Роль | Что ещё |
|---|---|---|---|
| `user@demo.local` | `demo1234` | `USER` | `account_status=ACTIVE` |
| `creator@demo.local` | `demo1234` | `CREATOR` | `account_status=ACTIVE`, персона включена |

Пароль — заранее посчитанный BCrypt-хеш, вписанный в скрипт константой; иначе для сеанса
понадобился бы запуск Java. Скрипт идемпотентен (`ON CONFLICT (email) DO UPDATE`), id не
фиксирует — стенд узнаёт их через `/api/user/me`.

Персона креатора засевается сразу включённой и с `greeting`, чтобы первый же диалог начался
с приветствия — это проверяет `sendPersonaGreeting` без ручной настройки.

## 6. Модули

Пять единиц, каждая с одной задачей. Все зависимости — вниз по списку.

### `lib/api.ts` — транспорт

Единственное место, где живут `credentials: "include"`, базовый URL и разбор ошибок.

Форма ошибки задана бэкендом — `GlobalExceptionHandler` отдаёт `ApiError` на все случаи:

```ts
type ApiError = {                   // ровно то, что строит GlobalExceptionHandler.build()
  status: number;
  error: string;                    // reason phrase, напр. "Bad Request"
  message: string;
  path: string;
  timestamp: string;
};
async function api<T>(path: string, init?: RequestInit): Promise<T>;
```

Бросает `ApiError` на не-2xx. `401` не перехватывает — это делает слой сессии.

Два случая, где тела нет и разбор обязан их пережить: `POST /auth/forgot-password` и
`POST /auth/reset-password` возвращают `void`, а `401` от `HttpStatusEntryPoint`
(неаутентифицированный запрос) приходит вообще без тела — в отличие от `401` из
`GlobalExceptionHandler`, у которого тело есть. При пустом теле подставляем
`{status, error: response.statusText, message: response.statusText}`.

Полезная деталь для отладки: на `403` бэкенд намеренно отвечает невнятным
`"access denied"`, а настоящую причину вместе со списком authorities пишет в лог. Значит
`/studio`, открытая под `USER`, покажет глухое «access denied» — и это правильное
поведение, а не поломка стенда. Подписать на экране.

### `lib/session.tsx` — кто я

Контекст: `{ user: UserDto | null, login, logout, refresh }`. При старте зовёт
`/api/user/me`; `401` означает «не залогинен» и не считается ошибкой. `login` делает
`POST /auth/login` (кука выставляется ответом) и затем `refresh`.

Не хранит токен: он в httpOnly-куке, и это ровно то поведение, которое надо проверить.

### `lib/stream.tsx` — SSE

Один `EventSource` на вкладку, `withCredentials: true`, открывается после успешного
`/me`. Раздаёт события через контекст и держит журнал последних 200 штук для `/debug`.

```ts
type StreamState = {
  status: "connecting" | "open" | "closed";
  log: { at: number; event: string; data: unknown }[];
};
```

Именованные события: `message`, `reply-start`, `token`, `reply-end`, `error`.
Имена берутся из `ChatStreamEvent` бэкенда, продублированы в `lib/events.ts` константами.

### `lib/reply-reducer.ts` — сборка ответа (чистая функция, под тестом)

Самое хитрое место стенда, поэтому вынесено и покрыто тестами.

```ts
type ChatState = {
  messages: MessageResponse[];          // по возрастанию createdAt
  drafts: Record<string, string>;       // replyId → накопленный текст
  banner: string | null;                // ai_unavailable / rate_limited / internal
};
function reduce(state: ChatState, ev: StreamEvent): ChatState;
```

Правила, каждое — тест:

- `message` с уже известным id **не дублируется**: ответ персоны приходит и токенами, и
  отдельным `message`-событием.
- `token` дописывает в черновик по `replyId`.
- `reply-end` с `messageId` снимает черновик; сам текст придёт (или уже пришёл) в `message`.
- `reply-end` с `messageId: null` — отказ модели: черновик снять, дальше прилетит
  системное сообщение.
- `error` снимает черновик и поднимает баннер.
- События чужого диалога игнорируются: стрим один на все диалоги.

### `lib/upload.ts` — прямая загрузка (чистые части под тестом)

```ts
function planParts(file: File, partSize: number): Blob[];   // тестируется
async function uploadAsset(file: File, type: AssetType, onProgress): Promise<AssetResponse>;
```

Три шага по `docs/media-upload.md`: `POST /api/content/uploads` → PUT частей по 3
параллельно с обязательным `Content-Type: plan.contentType` → `POST .../complete` со
собранными ETag. При `403` на части — один раз перезапросить URL через
`POST /api/content/uploads/{id}/parts` и повторить. Отмена — `DELETE /api/content/uploads/{id}`.

Аватар персоны грузится простым `POST /api/content/upload` (multipart) — так покрыты оба пути.

## 7. Экраны и покрытие API

| Экран | Эндпоинты |
|---|---|
| `/` | `POST /auth/login`, `GET /api/user/me`, `POST /api/user/become-creator`, `PATCH /api/user/update/{id}`, `GET /api/interests`, `POST /api/user/interests`; сворачиваемый блок: `POST /auth/register`, `GET /auth/confirm`, `POST /auth/resend-confirmation` |
| `/studio` | `GET /api/persona`, `PUT /api/persona`, `POST /api/content/uploads`, `PUT /api/content/uploads/direct` (подписанный URL из плана; в проде это PUT прямо в R2), `POST .../parts`, `POST .../complete`, `DELETE /api/content/uploads/{id}`, `POST /api/content/upload`, `GET /api/content`, `GET /api/content/{id}`, `PATCH /api/content/{id}/metadata`, `DELETE /api/content/{id}` |
| `/feed` | `GET /api/feed`, `POST /api/feed/swipe`, `GET /api/feed/favorites`, `GET /api/content/{id}/file` (через `fileUrl` в `<video>`), `POST /api/chat/conversations` |
| `/chats` | `GET /api/chat/conversations` |
| `/chats/[id]` | `GET /api/chat/conversations/{id}/messages`, `POST .../messages`, `POST .../read` |
| весь стенд | `GET /api/chat/stream` |

В бэкенде 34 эндпоинта плюс новый `/api/user/me` — 35. Стенд не трогает **три**: сброс
пароля (раздел 10). Остальные 32 покрыты.

### Что должно быть видно на `/chats/[id]`

- пузырь с бейджем **«из клипа #N»** по `contextAssetId` — это доказательство, что видео
  доехало до промпта;
- системные сообщения отдельным стилем: `senderType=SYSTEM` — это платформа, не персона;
- селектор клипа рядом с полем ввода — отправить сообщение с `assetId` можно в любой момент,
  контекст хранится на каждом сообщении, а не на диалоге;
- бейдж «AI» в шапке, когда `personaEnabled=false` — стенд обязан не обещать ответ,
  которого не будет.

## 8. Обработка ошибок

Стенд по умолчанию **не глотает ничего**. Единая полоса вверху экрана: код, эндпоинт, тело.

Отдельно разобраны состояния, где молчание — худший исход:

| Ситуация | Что показать |
|---|---|
| `error: ai_unavailable` | «Ключ OpenAI не настроен — персона не ответит» |
| `error: rate_limited` | «Потолок 12 ответов в минуту на диалог» |
| `error: internal` | текст + отсылка к логам бэкенда |
| стрим закрылся | индикатор `closed` и кнопка reconnect на всех экранах |
| `POST /swipe` дважды по одному ассету | 400 показать как есть, не считать поломкой |
| `personaEnabled=false` | не рисовать черновой пузырь вообще |

Стенд проверяется руками — это его предназначение. Автотесты только там, где ошибка

`UserControllerTest` — на стороне бэкенда, по TDD, как остальные задачи плана.

## 10. Не покрыто, сознательно

- **Сброс пароля** (`forgot-password`, `validate-reset-token`, `reset-password`) — нужен
  доступ к почтовому ящику, а при seed-аккаунтах путь бессмысленен.
- **Мультиинстанс.** Реестр SSE-эмиттеров живёт в памяти JVM. Стенд бьётся в один
  процесс; за балансировщиком без sticky sessions работать не будет.
- **R2 и CDN.** Дев-режим (`r2.enabled=false`) держит файлы на диске и отдаёт подписанные
  `/api/content/uploads/direct`. Клиентский код от этого не зависит, но и настоящий CDN
  стенд не проверяет.
- **Модерация, оплата, возрастные гейты.** В бэкенде их пока нет.

## 11. Подводные камни

1. **Инкогнито обязательно.** Кука одна на хост; два обычных окна перезатрут друг другу
   сессию, и клиент решит, что стенд сломан. Первый абзац README.
2. **Ключ OpenAI.** Без `OPENAI_API_KEY` бин провайдера не создаётся, и каждое сообщение
   отвечает `ai_unavailable`. Проверять до демонстрации.
3. **Миграции.** `scripts/migrations/001` и `002` обязательны на свежей базе: `ddl-auto`
   не переписывает CHECK-констрейнты, и статус `UPLOADING` будет отвергнут.
4. **Первое сообщение от креатора не вызывает AI.** Это осознанное правило бэкенда:
   пишет человек — персона молчит. Подписать на экране, иначе выглядит как баг.
5. **Потолок 4000 символов** на сообщение и обрезка ответа модели по `max-reply-tokens`.
6. **`app.base-url`** в дев-конфиге — `http://localhost:3000/app`, то есть ссылки
   подтверждения из писем ведут на порт стенда. Роут `/app/confirm` не делаем, но знать
   стоит: если клиент всё же зарегистрируется сам, ссылка приведёт в 404.
